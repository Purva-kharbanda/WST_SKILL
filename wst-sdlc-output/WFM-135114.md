## Probable cause

- **Symptom:**     On the Request Calendar, after opening an existing Time Off or Day Off request and saving with the Due By Date field blank, the Due By Date remains blank (NULL) instead of being set to the effective date.
- **Fault:**       `WebContent/scripts/request.calendar.renderers_new.js:saveRequest():5645,5720` â€” the Day Off and Time Off edit branches build `dueByDateSkey` as `$rfx.dateSkey(parseDate(vm.selectedRequest.formattedDueDate))` with no fallback when `formattedDueDate` is empty, producing `0`.
- **Trigger:**     User opens an existing Time Off or Day Off request via the Request Calendar (ESS or SM), either clears the Due By Date field or opens a request that already had no due date, and saves.
- **Consequence:** `dueByDateSkey = 0` is sent in the request body â†’ `RwsEmployeeLeaveRequestDTO.setDueByDateSkey(0)` skips storage (guard: `if (dueByDateSkey > 0)` fails) â†’ `dueBy` stays `null` â†’ `RwsEmpAvailableDB` UPDATE writes `DUE_BY = NULL` â†’ the column remains null after save, violating the expected default-to-effective-date behavior.

**Supporting code chain:**

1. **Edit path sends 0 (broken):**
   ```javascript

   'dueByDateSkey': $rfx.dateSkey(parseDate(vm.selectedRequest.formattedDueDate)),
   // When formattedDueDate = "" â†’ parseDate("") = null â†’ dateSkey(null) = 0
   ```

2. **DTO setter silently ignores 0:**

### Root cause

When editing a Time Off or Day Off request on the Request Calendar with the Due By Date field left blank, the edit save path sent a zero-value date key to the server instead of defaulting to the effective date â€” because the edit path lacked the blank-date fallback guard that the Add path already had. The server correctly rejected the zero value but silently left the Due By Date as null rather than substituting the effective date.

### Analysis

Users who opened an existing Time Off or Day Off request via the Request Calendar (ESS or Store Manager profile) and saved with the Due By Date field blank â€” either after manually clearing it or after opening a request that already had no due date â€” would find the Due By Date remained null after saving. The field did not reset to the effective date as expected. This issue affected only the edit flow; the Add (new request) flow already correctly defaulted to the effective date and was unaffected.

### Fix

- When saving an edited Time Off or Day Off request from the Request Calendar with the Due By Date field blank, the application now defaults the Due By Date to the effective date, matching the existing Add-path behavior.
- Both the Time Off and Day Off edit paths are covered by this change.
- Explicitly provided Due By Dates are saved unchanged â€” only the blank/empty case is affected.
